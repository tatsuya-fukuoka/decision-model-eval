# Hub カーネルの一致確認：判定基準（実行前に固定）

ユーザー承認：2026-11-09。この文書は実行の前にコミットし、実行後に閾値を変えない。

## 目的

d3-nano・d3-mini・Clef-Flash・d3-lite・d3-flash は、Hub カーネルを無効にした「参考値」で報告している。
公式の構成（`kernels-community/fla` v1 を `kernels.kernelize` で適用）でも同じ結果になるかを確かめる。

## 対象

- モデル：d3-nano、d3-mini、Clef-Flash、d3-lite、d3-flash（5モデル）
- データ：S1MB の重ならない17タスク（公式 CLI の `--benchmark` で指定）と bench_ja（部署・緊急度・解約示唆・解約示唆の言い換え版）

## 実行条件（モデルごとに4回）

| 条件 | 内容 |
| --- | --- |
| `nk1` | カーネルなし、bf16（`--no-hub-kernels`）。参考値と同じ構成 |
| `nk2` | `nk1` と同じ構成の2回目 |
| `k` | カーネルあり、bf16（公式の `enable_kernels`。`kernels-community/fla` v1 = `24d8640d`） |
| `f32` | カーネルなし、fp32（bf16 で読み込んだ後、バックボーンを fp32 に変換。チェックポイントのバックボーン重みは BF16 なので、fp32 で読み込んだ場合と重みの値は同じ） |

**追記（2026-11-09、ユーザー判断。閾値と比べ方は変えていない）：** 公式構成は fla に加えて
`kernels-community/activation` v1（SiLU・GELU 系。コンパイル済み CUDA バイナリ `.so`）を使う。これは内容を読んで確認できず、
ネイティブコードの通信は現環境では防げないため、実行しない。`k` は **fla のみ適用（activation は未適用）** とし、
bridge の `--exclude-kernel-repo kernels-community/activation` で、公式 `enable_kernels` の対応表から activation の項目だけを外す。
結果は「fla のみ適用（activation は未適用）」と書き、「公式構成と一致」とは書かない。activation を含む公式構成との一致は未確認とする。

4条件とも同じ隔離環境（`envs/kparity-open`、`envs/kparity-clef`）で実行する。`kernels==0.16.0` は lock で固定する。

## 比べる組と統計量

比べる組：
- **A**：`k` 対 `nk1`（判定の対象）
- **B**：`nk1` 対 `nk2`（同じ構成での再現性。参考）
- **C**：`nk1` 対 `f32`（数値精度によるばらつきの目安。基準4で使う）
- **D**：`nk1` 対 既存の参考値（`results/raw/<model>/`）。環境の作り直しで結果が変わっていないかの確認（参考）

統計量（S1MB 17タスクと bench_ja のそれぞれで計算する。両方の条件で予測が出た判断だけを使う）：
- **s1**：argmax の不一致率（同点のときは作者の順序で先の選択肢）
- **s2**：判断ごとの「選択肢の確率の絶対差の最大値」の 99 パーセンタイル
- **s3**：
  - S1MB：17タスクの Task Avg（公式の採点式）の差の絶対値
  - bench_ja：主要指標の差の絶対値の最大値。主要指標は、部署の正解率、緊急度の正解率と RPS、解約示唆の AUROC、言い換え版の AUROC
- **失敗**：失敗した判断の集合

## 「一致」の基準（組 A について。S1MB と bench_ja の両方で満たすこと）

1. s1 ≤ 0.005
2. s2 ≤ 0.01
3. s3 ≤ 0.005
4. s1・s2・s3 のそれぞれについて、組 A の値が組 C（bf16 と fp32 の差）の値の 2 倍以下であること（「同程度」の定義）。組 C の値が 0 のときは、組 A の値も 0 であること
5. 失敗した判断の集合が同じであること

扱い：
- 1〜5 をすべて満たしたモデルだけを「一致」と書く。
- 満たさない基準がある場合は「一致」と書かない。組 A と組 C の値を併記し、どの基準を満たさなかったかを書く。
- `f32` が実行できなかった場合（メモリ不足など）、基準4は「未判定」とし、そのモデルは「一致」と書かない。
- `k` の実行で Triton がこの GPU（RTX PRO 6000 Blackwell、compute capability 12.0）で動かなかった場合は、「公式構成では動作せず」と報告する（k は fla のみ適用なので、「fla のみ適用の構成では動作せず」と書く）。

## 実行環境の制約（承認済みの方法）

- 専用の非 root ユーザー（`kparity`）で、`env -i` で環境変数を空にして実行する。
- 書き込みを許すのは評価用ディレクトリ（`/srv/kparity`）だけ。カーネルは root 所有の読み取り専用ディレクトリ（`/srv/kparity-ro/kernels`）に置く。
- プロキシ設定はなし、`HF_HUB_OFFLINE=1`。
- Python の audit hook でソケット接続（AF_UNIX 以外）と名前解決を拒否し、記録する（`scripts/net_guard.py`）。
- コンテナに `CAP_SYS_ADMIN` / `CAP_NET_ADMIN` がないので、OS レベルのネットワーク遮断（`unshare -n`、iptables）は使えない。audit hook は Python から行う通信だけが対象で、ネイティブコードが直接行う通信は対象外である。
- `/tmp` と `/dev/shm` は、コンテナ内の全ユーザーが書き込める（名前空間を分けられないため）。`TMPDIR` などは評価用ディレクトリに向ける。
